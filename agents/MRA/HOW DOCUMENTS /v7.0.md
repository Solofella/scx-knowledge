## 1. Purpose and Role in the Pipeline

MRA is the terminal reporting agent in the 8-agent SCX pipeline (ALA → EIP → ESS → HSI → SIA → BRA → RDA → MRA). It does not feed forward into any other agent — MRA is where the pipeline's output becomes visible to the client. Every upstream agent's work (guest signal detection, emotional interpretation, response drafting, approval) is consumed here and converted into a human-readable report.

**Upstream relationships:**
- **ALA** — source of raw guest reviews; MRA reads ALA directly (Step 6) for review counts, star ratings, platform breakdown, filtered by `Date` (M/D/YY), never by pipeline processing timestamp.
- **RDA** — source of draft/approval status; MRA reads RDA directly (Step 8) for tier breakdown, SLA compliance, approval velocity, pending counts.
- **SIA** — source of clustered signal data for weekly/monthly reports (Step 10b), read via named reference, never `$input`. SIA also supplies the `getSignalTier()` reference logic that MRA's daily branch should be using but currently isn't (see §12, FIX 3).
- **EIP** — source of raw per-review signal classification for daily reports only (Step 10d), since daily's 24-hour window is too narrow for SIA's own clustering cadence.
- **ESS** — source of expression-mode classification (Step 10c), feeding the (currently daily-branch-only-rendered, weekly/monthly-computed-but-unused-in-`17a`) expression breakdown.
- **Client Config** — not an agent output, but the source of brand/location identity, approval routing, and (new) account grouping.

**Downstream relationship:** none within the agent pipeline. MRA's output is external-facing only — Brevo emails to human recipients, and NocoDB writes (weekly/monthly only) for audit/tracking purposes. No agent reads MRA's output.

**Reporting cadences:**
- **Daily** — 24-hour review summary. **Consolidated: one email per brand/account**, covering every location in that account (§5).
- **Weekly** — Monday intelligence brief, one email per location. **Currently sending-paused** for pilot stage (§13); processing and NocoDB writes continue.
- **Monthly** — 1st-of-month pattern report, one email per location. **Trigger disabled** in the live workflow (`Step 1c`, `Step 2c` both show `disabled: true`); confirmed inactive, not a documentation gap.

Zero AI calls throughout. All computation is deterministic JS aggregation plus HTML templating plus one Brevo send per account (daily) or per location (weekly/monthly, when active).

## 2. Architectural Principles

**Principle #1 — filter by guest-review posting date, not pipeline timestamp.** Every metric computation (`Step 9`) filters ALA/RDA records by ALA's own `Date` field (M/D/YY format, parsed and compared as local-midnight timestamps), not by when any pipeline agent processed the record. This ensures reports reflect what guests actually said and when, independent of processing delays anywhere upstream.

**Principle #2 — nested account/location loop (REVISED, replaces v5.0's flat design).** Client Config rows are grouped by `parent_account_id` (`Step 4a`) before looping. The outer loop (`Step 4b`) iterates once per account; a nested inner loop (`Step 4d`, fed by `Step 4c`) iterates once per location within that account. This structure is shared by all three report types — daily consolidates the inner loop's results into one email per account; weekly/monthly still send one email per location, but now route through the same nested-loop mechanics underneath.

**Principle #3 — single scheduled trigger fans out to all Client Config rows.** One workflow execution processes every active client; there is no per-client workflow instantiation.

**Separate workflow note:** SCX-Sheet-Sync (5am UTC) shares NocoDB tables with MRA but has no execution dependency in either direction.

## 4. Window Calculation — `Step 3`

```javascript
if (report_type === 'daily') {
  window_days = 1;
  period_end = now.toISOString();
  period_start = new Date(now.getTime() - 1 * 86400000).toISOString();
} else if (report_type === 'weekly') {
  window_days = 7;
  period_end = now.toISOString();
  period_start = new Date(now.getTime() - 7 * 86400000).toISOString();
} else {
  window_days = 30;
  const firstOfThisMonth = new Date(now.getFullYear(), now.getMonth(), 1);
  const firstOfLastMonth = new Date(now.getFullYear(), now.getMonth() - 1, 1);
  period_start = firstOfLastMonth.toISOString();
  period_end = new Date(firstOfThisMonth.getTime() - 1).toISOString();
}
```

- **Daily:** rolling 1-day window.
- **Weekly:** rolling 7-day window.
- **Monthly:** true calendar-month boundary (1st of last month through 1ms before 1st of this month) — **not** a rolling 30-day window, despite `window_days: 30` being assigned as a label. This label/logic mismatch is cosmetic (the label says 30, the actual boundary is calendar-based), not a functional bug.

**⚠️ Unresolved, unchanged from v5.0:** SIA's own monthly window is a genuine rolling 30-day window, not a calendar-month boundary. Since MRA's weekly/monthly branch reads SIA's cluster output directly (§8), MRA's monthly report label may describe a different date range than the underlying SIA data actually covers. Not reconciled; monthly is currently disabled regardless, lowering urgency.

`Step 3` also generates `mra_run_id` (format `MRA-YYYYMMDD-HHMMSS`) and `run_timestamp`, both threaded through the entire pipeline from here.

## 5. Account/Location Loop Architecture — `Step 4` through `Step 4d`

**This is the primary structural change since v5.0.** Business driver: pilot feedback indicated that 5 separate per-location daily emails per brand were burdensome; the fix consolidates them into one email per brand, scaling to however many locations that brand has (1, 5, 20+), with zero data mixing between different brands. No change to underlying metrics, calculations, or approval mechanism — layout consolidation only.

```
Step 4 - Fetch Client Config (HTTP, limit=100, unfiltered fetch of entire table)
 → Step 4a - Explode Client Array (Code)
    Groups Client Config rows by parent_account_id, falling back to
    Client ID for accounts with no explicit grouping (single-location
    clients are their own group of one — no special-casing anywhere
    downstream).
 → Step 4b - Split Clients for Processing (Split In Batches, batch=1)
    Outer loop — one iteration per ACCOUNT.
    → Step 4c - Explode Locations for Account (Code)
       Explodes the current account's locations[] array into N
       individual items. Tags each with:
         - is_first_in_account: (i === 0)
         - report_type: threaded from Step 3
         - parent_account_id: threaded from the account group
         - seo_keywords_raw: threaded from the Client Config row
       → Step 4d - Split Locations for Processing (Split In Batches, batch=1)
          Inner loop — one iteration per LOCATION within the current account.
          Reset parameter: {{ $json.is_first_in_account }}
          → Loop branch → Steps 5–13 (per-location processing, unchanged
            logic, now nested one level deeper than v5.0's flat design)
          → Done branch → 16e-gate (§6)
```

**Why `Step 4d`'s Reset expression is required — the critical lesson of this rebuild:** n8n's Split In Batches node retains internal state (current index, total item count, "no items left" flag) for the **entire duration of a single execution**, scoped to the node instance — it does not automatically detect that a structurally new batch of input has arrived from an outer loop. Nesting two Split In Batches nodes without explicit reset handling is a confirmed n8n anti-pattern for exactly this reason: without the reset, `Step 4d` would continue counting from wherever it left off on the *previous* account, producing zero loop-branch output and cross-account-contaminated done-branch output on every account after the first.

The fix — tagging the first location of each new account (`is_first_in_account`) and wiring that flag into `Step 4d`'s Reset parameter — forces a clean state reset exactly once per account, while preserving correct mid-account iteration for every subsequent location in that same account.

**Confirmed working via direct test:** after this fix, `Step 4d`'s Done branch correctly isolated a 1-location account from a 5-location account with zero cross-contamination, verified across multiple runs.

**A related, separately-investigated question — ruled out:** whether n8n execution state could bleed across two *separate* scheduled executions (e.g., an 8am daily run and a 9am weekly run) was investigated as a possible explanation for an unrelated symptom. Confirmed **not possible** — n8n execution state is strictly isolated per Execution ID. The actual cause of that symptom was a missing wire (§6), not shared state.

## 7. `16e - Aggregate Account Metrics` — Daily Consolidation Logic

Runs once per account, after `Step 4d`'s Done branch confirms every location in that account has finished processing. Produces the combined dataset `Step 17a` renders into one email.

**Live code (confirmed, Batch #6):**

```javascript
let all4c = [];
try {
  all4c = $('Step 4c - Explode Locations for Account').all().map(function(item) { return item.json; });
} catch (e) {
  return [{ json: { error: '4c failed: ' + e.message } }];
}

let allLoopResults = [];
try {
  allLoopResults = $('Step 4d - Split Locations for Processing').all().map(function(item) { return item.json; });
} catch (e) {
  return [{ json: { error: '4d failed: ' + e.message } }];
}

const currentAccountId = all4c.length > 0 ? all4c[all4c.length - 1].parent_account_id : null;

const expectedClientIds = {};
for (let i = 0; i < all4c.length; i++) {
  if (all4c[i].parent_account_id === currentAccountId) {
    expectedClientIds[all4c[i].client_id] = true;
  }
}

const locationResults = [];
for (let i = 0; i < allLoopResults.length; i++) {
  const item = allLoopResults[i];
  if (expectedClientIds[item.client_id]) {
    locationResults.push(item);
  }
}
// ... sums total_reviews, weighted blended_avg_rating, total_drafts
// (t_negative_count + t_ambiguous_count + t_positive_count), total_pending
```

**Design rationale, generalizable lesson:** `$(nodeName).all()` on any n8n node — Code or Split In Batches alike — returns that node's **entire execution history**, not just the current loop pass. `16e` cannot simply trust `Step 4d`'s accumulated Done-branch output as "just this account's locations" without filtering. The working solution cross-references `Step 4c`'s own accumulated history (which also grows across the execution) by matching `parent_account_id` against the most recently-added entry, using that to build an allow-list of `client_id`s, then filtering `Step 4d`'s full history down to just those IDs.

**Note on `total_drafts`:** computed as the sum of the three tier-count fields, which inherits the confirmed FIX 3 undercounting bug (§12) — some real drafts (Masked Negative, Dignity-Risk, Ambiguous Negative signal types) are not reflected in this sum, since `Step 11`'s daily branch never classifies them into any tier at all.

**A superseded, now-inert node in the same vicinity — `13b - Accumulate Location Result`:** confirmed live and actively wired (`Step 13 → 13b → both Step 14b and Step 14`), writing each location's result into `$getWorkflowStaticData('node').location_results`. This was an earlier attempted solution to the same per-account isolation problem `16e` ultimately solved differently (via the `4c`/`4d` cross-reference above). **`13b` runs on every single execution and does real work (writing to static data), but nothing downstream currently reads what it writes.** This is not a bypassed/disabled node — it is a live, harmless, but currently purposeless one. Candidate for removal in a future cleanup pass (§16, open item).

## 8. `Step 11 - Process SIA and SEO` — Conditional Data Source and Confirmed Bug

**Daily branch:** reads EIP (`Step 10d`), filtered against `filtered_ala_record_ids` (built in `Step 9`). Classifies each EIP record by `Signal Type`:

```javascript
if (signal_type === 'Positive Signal') {
  t_positive_count++;
} else if (signal_type === 'Negative Signal') {
  t_negative_count++;
} else if (signal_type === 'Mixed Signal' || signal_type === 'Ambiguous Signal') {
  t_ambiguous_count++;
}
```

**🔴 Confirmed bug, live in Batch #4 — FIX 3, verified and ready, NOT YET APPLIED:** this checks only 4 literal strings, and `'Ambiguous Signal'` matches nothing EIP actually produces. Three of EIP's six real `Signal Type` values — `Masked Negative Signal`, `Dignity-Risk Signal`, `Ambiguous Negative Signal` — fall through every condition and are silently uncounted, in both the tier tallies and the per-domain breakdown. Dignity-Risk is the platform's single most safety-critical signal category.

**Verified fix, sourced directly from SIA's own live code (`Step 11 - Build Clusters`):**

```javascript
function getSignalTier(signal_type) {
  if (['Dignity-Risk Signal','Negative Signal','Masked Negative Signal'].includes(signal_type))
    return 'T-NEGATIVE';
  if (['Ambiguous Negative Signal','Mixed Signal'].includes(signal_type))
    return 'T-AMBIGUOUS';
  return 'T-POSITIVE';
}
```

Confirmed to correctly map all 6 real values. Recommended fix: replace `Step 11`'s incomplete inline classification with this proven function — reuse, don't reimplement. Status: **diagnosis and fix both fully verified, code not yet applied, per Diagnose-Only Rule.**

**Weekly/monthly branch:** reads SIA clusters (`Step 10b`) via explicit named reference (never `$input`), filters to the latest `Run Timestamp` batch, aggregates by `Signal Tier` (already correctly using SIA's own `T-NEGATIVE`/`T-AMBIGUOUS`/`T-POSITIVE` values, since these come pre-classified from SIA rather than being reclassified here). Confirmed sound, no bug in this branch.

Also computes: top domains (sorted by total signal count), top 5 non-singleton trend signals (sorted by tier severity then volume, weekly/monthly only), SEO keyword-hit counting (scans `published_drafts`' raw text against `seo_keywords`), and expression-mode breakdown (from ESS, `Step 10c`).

## 9. `Step 9 - Process RDA Records` — Metric Computation and the Dead-`Published` Chain

`Step 7` ("Filter ALA by Window") is confirmed still a no-op — it passes `allRecords` through unfiltered as `ala_records` and hardcodes `total_records: 0, avg_star_rating: 0, platform_counts: {}` as literal placeholders. The name is misleading; this is cosmetic, not functional, because `Step 9` fully recomputes all three from scratch.

`Step 9` joins RDA↔ALA via `ALA Record ID`, filters by the real `period_start`/`period_end` window (using ALA's `Date` field, parsed from M/D/YY), and computes: `total_records`, `avg_star_rating`, `platform_counts`, tier breakdown (T1/T2/T3, each with total/approved/pending/avg_approval_hrs), SLA compliance rate, response velocity, and `all_time_pending` (a genuinely separate, all-history count, not scoped to the current window).

**🔴 Confirmed-dead metric chain, live in Batch #3, unchanged from v5.0:**

```javascript
let is_published = status === 'Published';
```

RDA's `Approval Status` field was simplified to 4 values (`Pending / Approved / Modify / Not Accepted`) — `Published` was removed entirely, and `Published Timestamp` is permanently null. This makes `published_count`, `sla_compliant`, `velocity_sum`, `velocity_count`, and `published_drafts` **permanently zero or empty, for every client, every report, forever** — cascading into `sla_compliance_rate`, `seo_avg_velocity_hrs`, `seo_response_rate`, `seo_top_keyword`, `seo_coverage_rate`, and `seo_keyword_hits`. This is broader than "SEO shows zero" — it also zeroes SLA compliance and response-time metrics.

**Harmless by contrast, confirmed same code:** `is_approved`/`is_pending` also reference deprecated status values (`Edited-Approved`/`Pending-Elevated`) but are OR'd with valid counterparts — vestigial, not broken.

**Blank-data effect, not a bug:** a blank Star Rating contributes 0 to the sum via `parseFloat(x||0)` while still counting in the denominator, silently dragging the average down — a data-completeness issue, not a calculation defect.

## 10. Passthrough Chains — Fields Requiring Explicit Threading

Per the established node-classification rule: fetch/HTTP nodes need no passthrough handling; non-rebuilding IF/Switch nodes pass items through unchanged; **Code nodes that reconstruct their return object key-by-key silently drop any field not explicitly listed.**

**`sheet_id`** — added at `Step 5`, threaded through Steps 7, 7b, 9, 10a, 11, 12, 13, 14, 16a (unchanged from v5.0).

**`parent_account_id`** — added this rebuild, threaded through Steps 5, 7, 7b, 9, 10a, 11, 12. **Confirmed, via direct Batch #5 read, that `Step 13` does NOT carry this field forward** — a real, confirmed gap. `16e`'s aggregation logic does not depend on `Step 13` carrying it (it sources `parent_account_id` from `Step 4c`'s own history instead), so this drop does not currently break the working daily flow, but it is a genuine passthrough gap, not a resolved item — flagged as an open item (§16).

**`report_type`** — added to `Step 4c`'s payload (read from `Step 3`), enabling `16e-gate`'s routing check. This field lives natively on the `Step 3 → 5 → ... → 13` chain but had no presence at all on the `Step 4/4a/4b/4c/4d` Client-Config-grouping chain until this addition, since that chain originally had no reason to know report type.

**`seo_keywords_raw`** — threaded from `Step 4a`'s per-location entry through `Step 4c`'s payload, then re-parsed into the `seo_keywords` array at `Step 5` (comma-split, trimmed, lowercased, filtered for empties) — restoring logic that previously ran directly on the raw NocoDB row before the account/location loop rework moved it one hop further from the source.

## 14. Delivery-Status Gating — `Step 19b` / `If` / `Step 20` / `19c`

This section required correction during the live-JSON confirmation (Batches #5–#8) versus what earlier session documentation assumed.

```
Step 19 - Update Delivery Status (Code — builds patch_body, unconditional "sent" status)
 → Step 19b - Gate Daily PATCH (Code — now a simple unconditional pass-through,
    confirmed simplified this session: return [{ json: s19 }]; only)
 → If (IF node — checks nocodb_record_id genuinely present, not the string "null")
    true  → Step 20 - NocoDB PATCH Delivery Status → loop back to Step 4d
             (weekly/monthly, per-location advance)
    false → 19c - Advance to Next Account → loop back to Step 4b
             (daily, per-account advance)
```

**Confirmed live in Batch #8:** `Step 19b`'s name is a holdover from an earlier design where it did its own conditional gating via `return []` — that logic has been **removed and replaced** by the separate `If` node, which uses an explicit boolean-expression check rather than n8n's string `notEmpty` operator. This change was required because `notEmpty` was found to evaluate a `null` value as passing (n8n renders `null` as the literal string `"null"`, which is technically non-empty) — a subtle bug that caused the true branch to incorrectly fire on every daily record, misrouting daily's account-advance signal through the weekly/monthly PATCH path instead of `19c`.

**Generalizable lesson:** a loop-back node must produce exactly one item, unconditionally, on every iteration — "last node in chain" is not sufficient if that node has any branch-specific zero-output condition. This applies at two nested levels in the current architecture: `Step 20`/`19c` for the outer account-advance decision, and (separately, upstream) `Step 4d`'s Reset expression for the inner per-location advance.

## 15. Locked Lessons — Consolidated, This Version

1. Filter by ALA Date, never RDA Timestamp.
2. `Step 11`'s conditional source must use named references, never `$input`.
3. `filtered_ala_record_ids` built at `Step 9`, consumed at `Step 11`'s daily branch.
4. Always `String()`-wrap ALA Record ID before comparison — type mismatches are silent.
5. A loop-back node must produce exactly one item unconditionally every iteration.
6. Field passthrough requires per-node classification — never assume automatic carry-through.
7. NocoDB field *type* constrains multi-value data — Email type ≠ multi-address capable; use LongText.
8. Google Sheet sharing settings are independent of correct URL routing — a Drive permission, not a workflow-code fix.
9. Blank source data silently distorts averages without any visible error.
10. `records[0]`-only patterns silently truncate multi-row fetches with zero errors.
11. **Nested Split In Batches nodes require explicit Reset handling** — n8n's internal state persists for the full execution, scoped to the node instance, and does not auto-detect a structurally new batch from an outer loop. Tag the first item of each new outer-loop iteration and wire it into the inner loop's Reset parameter as an expression.
12. **`$(nodeName).all()` on any node returns that node's entire execution history**, not just the current loop pass. Aggregation logic needing "just this iteration's items" requires explicit filtering against a reliable per-iteration key.
13. **A shared inner-loop node used by multiple report types needs an explicit report-type gate** before any report-type-specific downstream logic fires.
14. **HTML email layout should use tables, not flexbox**, for any structure that needs to survive Gmail's mobile app.
15. **Cross-execution state bleed in n8n is not a real phenomenon** — separate scheduled runs never share state; apparent interaction between them points to a wiring bug within one execution, not shared memory between two.
16. **n8n's string `notEmpty` operator can evaluate `null` as non-empty** (rendered as the literal string `"null"`) — use explicit boolean expressions for null-sensitive routing decisions instead.
