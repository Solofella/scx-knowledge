**SCX_MRA_HOW_v3.0**
Agent Name: MRA (Metrics & Reporting Agent)
Version: 3.0
Last Updated: Chat #89 · May 18, 2026
Model: Pure JavaScript (zero LLM calls)
Status: Production-ready — 30 nodes complete — Multi-client loop architecture

**Purpose**

MRA generates scheduled intelligence reports for ALL active clients on three cadences:
- 24-hour review summary (daily 8am UTC delivery)
- Weekly intelligence brief (Monday 9am UTC delivery)
- Monthly comprehensive report (1st of month 10am UTC delivery)

MRA uses pure JavaScript — zero AI calls, zero token cost. All computation is deterministic aggregation and formatting.

**CRITICAL ARCHITECTURE PRINCIPLE #1:** Reports filter by guest review posting date (ALA Date field), NOT by pipeline processing date (RDA Timestamp). This ensures reports reflect when guests actually posted reviews, not when VRYOH processed them.

**CRITICAL ARCHITECTURE PRINCIPLE #2 (NEW v3.0):** MRA processes ALL clients in Client Config in a single scheduled run via a Loop Over Items architecture. One schedule trigger fires once; the workflow internally loops once per client, generating and sending that client's report before moving to the next. No per-client schedule duplication. No manual re-trigger required as clients are added.

---

**What changed since v2.1 (Chat #82)**

v2.1 assumed single-client processing. Step 5 read `records[0]` from the Client Config fetch and discarded every other row. Adding a new client (EDO-001, AJI-001, etc.) required no code change to be picked up by the fetch, but only the FIRST row returned by NocoDB was ever processed — silently. This was not caught until Chat #88's audit because Client Config had only one active row (PAK-001) at the time.

v3.0 fixes this by exploding the Client Config array into individual items and looping over them with n8n's Loop Over Items node, processing each client's full pipeline (Steps 5→20) before the loop advances to the next client.

**Architecture Overview — 30 Nodes (was 28 in v2.1)**

Three Schedule Triggers (Node 1a/1b/1c):
- Daily: Every day 8am UTC → report_type = 'daily'
- Weekly: Every Monday 9am UTC → report_type = 'weekly'
- Monthly: 1st of month 10am UTC → report_type = 'monthly'

**Steps 1-5: Session initialization + multi-client loop entry (NEW in v3.0)**

- Step 1a/1b/1c: Trigger on schedule
- Step 2a/2b/2c: Set report_type (daily/weekly/monthly)
- Step 3: Calculate period window (2-day/7-day/30-day) and generate MRA Run ID
- Step 4: Fetch Client Config from NocoDB — ALL rows, no client filter, limit=100
- **Step 4a (NEW): Explode Client Array** — Code Node. Converts the single input item `{ list: [config1, config2, ...] }` into N separate n8n items, one per client config row. Required because Loop Over Items only iterates correctly across multiple items, not across an array nested inside one item.
- **Step 4b (NEW): Loop Over Items** (n8n's SplitInBatches equivalent in 2.4.6) — batchSize 1. Receives the N exploded items from Step 4a. Emits one client config at a time down output index 1 to Step 5. Output index 0 fires only when the loop is exhausted (unused in this workflow — no downstream node wired to it).
- Step 5: Extract client config + SEO keywords. Rewritten in v3.0 to accept a single config object directly from Step 4b (no longer indexes into a `.list` array under normal operation). Retains defensive handling for the case where `.list` is still present (legacy/manual test runs).

**Steps 6-10: Fetch data sources (per client, once per loop iteration)**

- Step 6: Fetch ALL ALA records for the current client (client_id from Step 5, no date filter in URL — filtering happens in Step 9)
- Step 7: Filter ALA by window (stores ala_records array for downstream use)
- Step 7b: Build RDA query URL (dynamic client_id)
- Step 8: Fetch ALL RDA records for the current client
- Step 9: CRITICAL DATE FILTERING NODE — Filter RDA by ALA Date matching, calculate star rating, platform counts, tier breakdown, all-time pending. Builds `filtered_ala_record_ids` array.
- Step 10a: Build SIA query URL by report_type + dynamic client_id
- Step 10b: Fetch SIA clusters (weekly/monthly window, current client only)
- Step 10c: Fetch ESS records (current client only, for expression modes)
- Step 10d: Fetch EIP records (current client only, for daily signal aggregation)

**Step 11: CONDITIONAL PROCESSING NODE**

- Daily branch: Aggregate from EIP records filtered by `filtered_ala_record_ids` from Step 9
- Weekly/Monthly branch: Aggregate from SIA clusters (latest run from Step 10b, explicit node reference — not `$input`)
- Both paths: Calculate expression modes from ESS, SEO keyword hits, domain totals

**Steps 12-16: Build report data**

- Step 12: Generate magic link token + expiration (72 hours)
- Step 13: Check report type (sets skip_nocodb flag for daily)
- Step 14: Route daily reports (IF node)
- Step 14b: Catch daily reports (FALSE branch gate)
- Step 15: NocoDB POST (weekly/monthly only)
- Step 16a: Extract NocoDB record ID
- Step 16b: Route to daily email builder (IF node)
- Step 16c: Route to weekly email builder (IF node)
- Step 16d: Route to monthly email builder (IF node)

**Steps 17+: Email generation & delivery**

- Step 17a: Build daily HTML email
- Step 17b: Build weekly HTML email (includes trend signals, SEO metrics)
- Step 17c: Build monthly HTML email (30-day patterns)
- Step 17d: Prepare for Send — merge point. Receives output from whichever of 17a/17b/17c fired, passes clean single payload to Step 18. Exists so Step 19 has one consistent upstream reference regardless of report type.
- Step 18: Send email via Brevo API
- Step 19: Update Delivery Status (in-memory field set)
- Step 19b: Gate Daily PATCH — FALSE branch gate. Daily reports do not write to NocoDB (no record was created at Step 15), so this gate prevents Step 20 from firing a PATCH against a non-existent record ID when report_type = daily.
- Step 20: NocoDB PATCH Delivery Status (weekly/monthly only)

**LOOP CLOSURE (NEW v3.0):** Step 20's output wires back to Step 4b (Loop Over Items), NOT to a workflow end. This tells the loop to advance to the next client config item. When Step 4b has no items left, the branch terminates naturally (output index 0, unwired).

Error Handler: 3 nodes (trigger, log, email notification) — unchanged from v2.1, operates outside the loop.

**Step 4a / Step 4b — Multi-Client Loop Architecture (NEW v3.0, built Chat #88)**

*Why this was needed:*

Step 4 (Fetch Client Config) returns ALL rows from the Client Config table in a single NocoDB response: one n8n item containing `{ list: [config1, config2, config3, ...] }`. Prior to v3.0, Step 5 read `records[0]` directly — every client after the first row in the table was silently never processed. No error was thrown because `records[0]` always exists as long as at least one config row exists.

This bug was invisible during the PAK-001-only pilot period because Client Config had exactly one row. It would have surfaced silently the moment a second client (EDO-001 or AJI-001) was added to Client Config — reports would have continued to look correct for PAK-001, and EDO-001/AJI-001 would simply never receive anything, with no error logged.

**Step 4a — Explode Client Array**
Type: Code Node
Position: Between Step 4 and Step 4b

```javascript
const input = $input.first().json;
const records = input.list || [];

if (records.length === 0) {
  throw new Error('MRA: No Client Config found in database');
}

const items = [];
for (let i = 0; i < records.length; i++) {
  items.push({ json: records[i] });
}

return items;
```

Input: 1 item, `{ list: [config1, config2, config3] }`
Output: N items, one per client config row.

This step exists because n8n's Loop Over Items node iterates over the ITEMS array it receives, not over a JS array nested inside a single item's json payload.

**Step 4b — Loop Over Items** (n8n 2.4.6 name for SplitInBatches)
Type: n8n-nodes-base.splitInBatches (internal type; UI label "Loop Over Items")
Batch Size: 1 (matches project-wide SplitInBatches=1 convention used in ALA)
Position: Between Step 4a and Step 5

Output wiring:
- Output index 0 ("done"): fires once, when all items have been processed. Unwired — no further action needed.
- Output index 1 ("loop"): fires once per item, sends the current client config to Step 5. Only this output is wired downstream.

**Loop-back connection:** Step 20 (NocoDB PATCH Delivery Status) → Step 4b. After a client's full report is built and sent, execution returns to Step 4b, which emits the next client config down output index 1. When no items remain, output index 0 fires (unwired) and that execution branch ends.

**Step 11 Architecture — Conditional Processing (Chat #82 Fix, unchanged in v3.0)**

Problem (Chat #82): Step 11 was reading from `$input` (Step 10d — EIP) for ALL report types, causing weekly/monthly reports to show 0 signal counts.

Solution: explicit conditional branching on `report_type`. Unaffected by v3.0 loop architecture — operates identically per-client, once per loop iteration.

*Daily branch (EIP records, filtered by `filtered_ala_record_ids`):*
```javascript
if (report_type === 'daily') {
  const eip_records = s10d.list || [];
  const filtered_ids = s9.filtered_ala_record_ids || [];

  const id_set = {};
  for (let i = 0; i < filtered_ids.length; i++) {
    id_set[String(filtered_ids[i])] = true;
  }

  for (let i = 0; i < eip_records.length; i++) {
    let rec = eip_records[i];
    let ala_id = String(rec['ALA Record ID'] || '');
    if (!id_set[ala_id]) continue;

    let signal_type = (rec['Signal Type'] || '').trim();
    let domain = (rec['Domain'] || '').trim();

    if (signal_type === 'Positive Signal') t_positive_count++;
    else if (signal_type === 'Negative Signal') t_negative_count++;
    else if (signal_type === 'Mixed Signal' || signal_type === 'Ambiguous Signal') t_ambiguous_count++;

    if (!domain_map[domain]) {
      domain_map[domain] = { domain: domain, neg: 0, amb: 0, pos: 0, total: 0 };
    }
    domain_map[domain].total++;
  }
  trend_signals_top5 = [];
}
```

*Weekly/Monthly branch (SIA clusters via explicit node reference):*
```javascript
} else {
  const sia_input = $('Step 10b - Fetch SIA Clusters').first().json;
  const allClusters = sia_input.list || [];
  const latestRunTs = allClusters.length > 0 ? allClusters[0]['Run Timestamp'] : null;

  const clusters = [];
  for (let i = 0; i < allClusters.length; i++) {
    if (allClusters[i]['Run Timestamp'] === latestRunTs) {
      clusters.push(allClusters[i]);
    }
  }

  for (let i = 0; i < clusters.length; i++) {
    let cl = clusters[i];
    let tier = (cl['Signal Tier'] || '').trim();
    let domain = (cl['Domain'] || '').trim();
    let n = parseInt(cl['N'] || 0);

    if (tier === 'T-NEGATIVE') t_negative_count += n;
    else if (tier === 'T-AMBIGUOUS') t_ambiguous_count += n;
    else if (tier === 'T-POSITIVE') t_positive_count += n;

    domain_map[domain].total += n;
  }

  for (let i = 0; i < clusters.length; i++) {
    if (!clusters[i]['Is Singleton']) {
      trend_signals.push({
        domain: clusters[i]['Domain'],
        tier: clusters[i]['Signal Tier'],
        n: clusters[i]['N'],
        prior_n: clusters[i]['Prior N'],
        trend_direction: clusters[i]['Trend Direction']
      });
    }
  }
}
```

*Expression Mode Aggregation (shared by both branches):*
```javascript
const ess_records = s10c.list || [];
const filtered_ala_ids = s9.filtered_ala_record_ids || [];

const ess_map = {};
for (let i = 0; i < ess_records.length; i++) {
  let alaId = String(ess_records[i]['ALA Record ID'] || '');
  let expr = (ess_records[i]['Expression Mode'] || 'Absent').trim();
  ess_map[alaId] = expr;
}

const expression_modes = {
  'Explicit': 0, 'Implicit': 0, 'Masked': 0,
  'Performative': 0, 'Conflicted': 0, 'Absent': 0
};

for (let i = 0; i < filtered_ala_ids.length; i++) {
  let alaId = filtered_ala_ids[i];
  if (ess_map[alaId]) {
    expression_modes[ess_map[alaId]]++;
  } else {
    expression_modes['Absent']++;
  }
}
```

Output schema (identical for both paths, per client, per loop iteration): `t_negative_count`, `t_ambiguous_count`, `t_positive_count`, `top_domains`, `trend_signals`, `expression_modes`, `seo_keyword_hits`, `seo_top_keyword`, `seo_coverage_rate`.

**Key Locked Lessons (Chat #78-88, consolidated)**

1. **Date Filtering by Source Timestamp** — filter by ALA Date, never RDA Timestamp.
2. **Step 11 Conditional Data Source** — daily=Step 10d(EIP), weekly/monthly=Step 10b(SIA) via explicit node reference, never `$input`.
3. **SIA Window Type Alignment** — Step 10a filters by both Client ID and Report Window Type.
4. **all_time_pending Field Chain** — calculated separately in Step 9 from ALL RDA records for current client, carried through Steps 9→10a→11→12→13→16.
5. **filtered_ala_record_ids Array** — built in Step 9, used by Step 11's daily branch to filter EIP records by date window.
6. **HTML Email Client Compatibility** — inline styles required on CTA/links.
7. **M/D/YY Date Parsing** — ALA Date is never ISO 8601; parse manually.
8. **Type Safety (String vs Integer)** — always wrap ALA Record ID in `String()` for comparisons.
9. **Multi-Recipient Email Support** — Brevo parses comma-separated Approval Contact Email automatically; per-client.
10. **NEW v3.0 — Array-in-Single-Item vs Multi-Item Loop Requirement:** Loop Over Items iterates over the items array it receives, not a JS array nested inside one item's json. An explode Code Node (Step 4a) is required before Loop Over Items will iterate per-record.
11. **NEW v3.0 — Silent Truncation Risk of `records[0]` Patterns:** This pattern against a "get all" NocoDB response works with zero errors as long as there's exactly one row, and silently drops every row after the first once a second row exists. Confirmed and fixed in MRA Step 5 (Chat #88). Recommend auditing BRA, RDA, and any other agent that bulk-fetches Client Config or similar shared/reference tables.
12. **NEW v3.0 — Loop-Back Wiring Convention:** The node terminating one client's chain (Step 20) must wire back to Loop Over Items (Step 4b) — not to a dead end or duplicate end node. Loop Over Items tracks iteration state internally.
