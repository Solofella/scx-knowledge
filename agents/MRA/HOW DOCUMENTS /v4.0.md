**SCX_MRA_HOW_v4.0**
Agent Name: MRA (Metrics & Reporting Agent)
Version: 4.0
Last Updated: Chat #105 · July 19, 2026
Model: Pure JavaScript (zero LLM calls)
Status: Production-live — 30 nodes — Multi-client loop, execution-confirmed across daily, weekly, and monthly cadences

**Purpose**

MRA generates scheduled intelligence reports for ALL active clients on three cadences:
- 24-hour review summary (daily 8am UTC delivery)
- Weekly intelligence brief (Monday 9am UTC delivery)
- Monthly comprehensive report (1st of month 10am UTC delivery)

MRA uses pure JavaScript — zero AI calls, zero token cost. All computation is deterministic aggregation and formatting.

**CRITICAL ARCHITECTURE PRINCIPLE #1:** Reports filter by guest review posting date (ALA Date field), NOT by pipeline processing date (RDA Timestamp).

**CRITICAL ARCHITECTURE PRINCIPLE #2:** MRA processes ALL clients in Client Config in a single scheduled run via a Loop Over Items architecture. One schedule trigger fires once; the workflow internally loops once per client. **As of v4.0, this is execution-confirmed across all three report types (daily, weekly, monthly), against real multi-client production data (PAK-001 + AJI-001 through AJI-005) — not just wiring-verified.** This is the key status change from v3.0, where the loop was structurally complete but had only been tested on weekly reports.

**Note on related but separate workflow:** SCX-Sheet-Sync is a distinct n8n workflow (its own 5am schedule, its own dedup/append logic to each client's Google Sheet) that shares some NocoDB tables with MRA but has no execution dependency in either direction. It is not covered in this document.

**What changed since v3.0 (Chat #89)**

Three real defects were found and fixed via live production testing between Chat #89 and this document, plus one required data-model change:

1. **Daily reports silently stopped after the first client** (Chat #100) — root cause: the loop-back wire was attached to Step 20, which legitimately produces zero output items for daily reports (they skip the NocoDB PATCH by design). Zero items reaching Step 4b's loop input halted the loop after client #1, with no error surfaced anywhere. Fixed by moving the loop-back wire to Step 19 instead (see Loop Architecture section below).
2. **Daily report window used a 2-day offset while labeled `window_days = 1`** (Chat #103) — caused each daily "New Reviews" count to silently double-count any review dated on the prior day's report window, since consecutive daily runs overlapped by one day. Fixed by changing the offset multiplier from 2 to 1 in Step 3.
3. **Every client's "View & Approve Drafts" button linked to PAK-001's Google Sheet**, regardless of which client's report it was in (Chat #99 diagnosis, Chat #100 fix) — Step 17a/17b had the sheet URL hardcoded as a literal string. Fixed by adding `sheet_id` to Client Config passthrough and building the URL dynamically per client.
4. **Multi-recipient email support did not actually work** (Chat #101) — prior documentation (v3.0, Lesson 9) claimed Brevo auto-parses comma-separated addresses; direct code read showed this was never implemented — only a single address was ever placed in Brevo's `to[]` array. Fixed by adding explicit split/trim logic in Step 17a/17b/17c, and changing Client Config's Approval Contact Email field from NocoDB's Email type to LongText (Email type likely rejects or mishandles multi-address strings).

**Architecture Overview — 30 Nodes (unchanged count from v3.0 — all v4.0 fixes were wiring/logic changes, no new nodes)**

Three Schedule Triggers (Node 1a/1b/1c):
- Daily: Every day 8am UTC → report_type = 'daily'
- Weekly: Every Monday 9am UTC → report_type = 'weekly'
- Monthly: 1st of month 10am UTC → report_type = 'monthly'

- Step 10c: Fetch ESS records — pure fetch, no passthrough needed
- Step 10d: Fetch EIP records — pure fetch, no passthrough needed

**Step 11: CONDITIONAL PROCESSING NODE** (daily=EIP via Step 10d, weekly/monthly=SIA via Step 10b named reference). **CHANGED v4.0:** passes `sheet_id` through in its rebuilt return object.

**Steps 12-16: Build report data**

- Step 19: Update Delivery Status (in-memory field set). **CHANGED v4.0 — CRITICAL:** this node's output is now wired to **two** downstream destinations: (a) Step 19b, unchanged; (b) **Step 4b directly (NEW loop-back path)** — see Loop Architecture section below for why.

**Loop Architecture — Step 4a/4b, and the v4.0 Loop-Back Fix**

*Original v3.0 design (Chat #88):* Step 20 wired back to Step 4b, on the reasoning that Step 20 is the last node in each client's chain.

*Defect discovered via live testing (Chat #100):* This reasoning held for weekly/monthly reports (which always produce exactly one item at Step 20), but daily reports are designed to skip the NocoDB PATCH entirely — Step 19b's `if (!s19.nocodb_record_id) return [];` correctly produces zero items for daily, and Step 20 correctly does nothing with zero items. But with **zero items reaching Step 4b's loop input**, Loop Over Items had nothing to advance on — the loop silently stopped after the first client, every time, for every daily run, with no error visible anywhere in the execution log. This went undetected through Chat #89 because every full-loop test before Chat #100 had been a weekly run.

*Fix applied (Chat #100):* Loop-back moved to **Step 19** — the last node in the chain that unconditionally produces exactly one item, every time, for every report_type (confirmed directly from its code: a single Code Node with one fixed `return [{ json: {...} }]`, no IF/Switch, no filtering).

```
Step 19 → Step 19b (unchanged — still gates the PATCH)
Step 19 → Step 4b (NEW — this is now the loop-back)
Step 19b → Step 20 (unchanged — fires only weekly/monthly)
Step 20 → Step 4b (REMOVED)
```

*Result, confirmed via live test:* daily reports for PAK-001 + all 5 AJI locations were received correctly in one run after this fix, closing out what had been the most serious open item in v3.0's "Known Issues" section.

**sheet_id Passthrough Chain (NEW, v4.0)**

Client Config's Sheet ID field existed in the schema since early in the project but was never read into the MRA payload. To surface each client's own Google Sheet in the approval email button, `sheet_id` needed to be added at the point of extraction (Step 5) and then explicitly carried through **every node that rebuilds its return object field-by-field** — Steps 7, 7b, 9, 10a, 11, 12, 13, 14, 16a.

**Node categorization established during this fix (useful pattern for future similar additions):**
- **HTTP Request / fetch nodes** (Steps 6, 8, 10b, 10c, 10d, 15) — never need a field added; they don't rebuild payloads, they either fetch fresh data or use named references (`$('Step 5 - ...').first().json.field`) to reach back to an earlier node directly.
- **IF/Switch/routing nodes that don't rebuild the object** (Step 14b, 16b/16c/16d) — pass the existing item through unchanged; no code change needed.
- **Code Nodes that explicitly reconstruct their return object key-by-key** (Steps 5, 7, 7b, 9, 10a, 11, 12, 13, 14, 16a) — any field not explicitly listed in that reconstruction is silently dropped, regardless of whether it existed on the input. This is the category that needed the one-line addition (`sheet_id: <upstream>.sheet_id`) at each hop.

This same category distinction is worth checking any time a new field needs to travel through this pipeline in the future — walk the chain node by node and classify each one before assuming a field survives automatically.

**Multi-Recipient Email Fix (NEW, v4.0)**

*Prior documented assumption (v3.0, now confirmed false):* "Brevo parses comma-separated Approval Contact Email automatically."

*Actual prior code (Steps 17a/17b/17c, confirmed via direct read, Chat #101):*
```javascript
const brevo_to = {};
brevo_to['email'] = s16.approval_email || 'miguel@solofella.com';
brevo_to['name'] = client_name;
const brevo_to_arr = [];
brevo_to_arr.push(brevo_to);
```
This placed the entire raw string — however many addresses it contained, whatever separator was used — into a single `email` field of a single recipient object. No split logic existed anywhere.

*Fix applied to all three (17a, 17b, 17c):*
```javascript
const raw_emails = s16.approval_email || 'miguel@solofella.com';
const email_list = raw_emails.split(/[,;]/).map(e => e.trim()).filter(e => e.length > 0);

const brevo_to_arr = [];
for (let i = 0; i < email_list.length; i++) {
  const recipient = {};
  recipient['email'] = email_list[i];
  recipient['name'] = client_name;
  brevo_to_arr.push(recipient);
}
```
Splits on either comma or semicolon, trims whitespace, filters empty entries, builds one `{email, name}` object per address.

**Supporting data-model change:** Client Config's Approval Contact Email field type changed from NocoDB "Email" (single-address validated type) to "LongText" — consistent with the pattern already used for other multi-value fields in the same table (SEO Keywords, Brand Phrases To Include/Avoid).

**Fallback behavior note (unresolved decision, not a defect):** if a client's Approval Contact Email is blank, the code defaults to sending that client's report to `miguel@solofella.com`. This was raised as an open question — whether that's the desired behavior long-term, versus erroring/skipping — and has not yet been explicitly decided.

**Key Locked Lessons (consolidated, Chats #78-105)**

1. Date Filtering by Source Timestamp — filter by ALA Date, never RDA Timestamp.
2. Step 11 Conditional Data Source — daily=Step 10d(EIP), weekly/monthly=Step 10b(SIA) via explicit node reference, never `$input`.
3. SIA Window Type Alignment — Step 10a filters by both Client ID and Report Window Type.
4. all_time_pending Field Chain — calculated in Step 9 from ALL RDA records for current client, carried through Steps 9→10a→11→12→13→16.
5. filtered_ala_record_ids Array — built in Step 9, used by Step 11's daily branch.
6. HTML Email Client Compatibility — inline styles required on CTA/links.
7. M/D/YY Date Parsing — ALA Date is never ISO 8601; parse manually.
8. Type Safety (String vs Integer) — always wrap ALA Record ID in `String()` for comparisons.
9. **CORRECTED v4.0 — Multi-Recipient Email Support:** Brevo does NOT auto-parse comma-separated strings — this must be done explicitly in code (split/trim/filter), confirmed by direct code read after the v3.0 claim proved false in practice.
10. Array-in-Single-Item vs Multi-Item Loop Requirement — Loop Over Items iterates over the items array it receives, not a JS array nested inside one item's json. An explode Code Node (Step 4a) is required first.
11. Silent Truncation Risk of `records[0]` Patterns — works with zero errors as long as there's exactly one row, silently drops every row after the first. Confirmed and fixed in MRA Step 5. Recommend auditing BRA, RDA, and other agents that bulk-fetch Client Config or similar shared tables.
12. **REVISED v4.0 — Loop-Back Wiring Convention:** The node wired back to Loop Over Items must produce **exactly one item, unconditionally, on every iteration, regardless of any branch-specific logic** — not simply "the last node in the chain." A node that legitimately produces zero items under some valid condition (like a report-type gate) is unsafe as a loop-back point, even if it usually produces one item. Confirmed via the Step 20→Step 19 loop-back relocation.
13. **NEW v4.0 — Field Passthrough Requires Per-Node Classification:** When adding a new field to a payload partway through a long Code Node chain, each downstream node must be individually classified as (a) a pure fetch/HTTP node — no passthrough needed, (b) a non-rebuilding IF/Switch — no passthrough needed, or (c) a Code Node that explicitly reconstructs its return object — needs the field added by hand at every such hop. Assuming a field "just carries through" without this check is how `sheet_id` almost shipped broken.
14. **NEW v4.0 — NocoDB Field Type Constrains Multi-Value Data:** A field typed as "Email" in NocoDB is a validated single-address type; multi-address strings (needed for multiple approval recipients) require a LongText field instead, consistent with how other multi-value fields (SEO Keywords, Brand Phrases) are already typed in this same table.
15. **NEW v4.0 — Google Sheet Sharing Is Independent of Correct URL Routing:** Even after a sheet_url correctly resolves to the right per-client document, external recipients will hit a Google "request access" wall unless that document's own Drive sharing setting is changed to "Anyone with the link" (or the recipient is added as an explicit collaborator). This is a Drive permission setting, not something fixable in workflow code.
16. **NEW v4.0 — Missing Source Data Silently Zeroes Averages, Not a Pipeline Bug:** A blank Star Rating field on an ALA record contributes `0` to `avg_star_rating`'s sum via `parseFloat(x || 0)`, while still counting toward the denominator — dragging the average down without any visible error. Confirmed via live diagnosis (AJI-003, 2.5 shown instead of a true 5.0) and resolved by filling in the missing source values, not a code change. Worth checking data completeness before assuming a calculation defect when an average looks implausible.
