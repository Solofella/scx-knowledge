## 1. PURPOSE

BRA is the fifth agent in the pipeline. It receives a behavioral tier assignment from HSI and produces a structured response strategy — axis framing, tone calibration, urgency level, governance assessment, and internal signal-based consideration — that RDA uses to draft the public-facing response.

**BRA does not draft the public response.** That is RDA's role. BRA produces the strategic layer RDA builds on.

**Governance principle (locked, permanent):** VRYOH detects and interprets signal only. BRA never prescribes operational actions. `signal_based_consideration` is internal guidance — never client-visible, never a directive.

**Hybrid architecture, by design:**
- **T1 (~70-80% of records):** Deterministic template selection via seeded hash on `hsi_record_id`. Zero AI cost. No Claude call. Reproducible and auditable — same `hsi_record_id` always selects the same template.
- **T2/T3 (~20-30% of records):** One Claude API call producing 7 structured JSON fields, governance-constrained.

**Both tiers converge at the same governance checkpoint (Step 10) and follow the same write/handoff path (Steps 11–19).** This is confirmed as of this version — see Section 3 and Section 9.

## 2. RELATIONSHIP TO PRECEDING AND SUBSEQUENT AGENTS

**Upstream — HSI (Human/Hospitality Signal Intelligence):**
HSI performs the full multi-factor tier routing decision before BRA ever sees a record. BRA does not recalculate tier — `preliminary_response_tier` arrives as final from HSI and is validated (not derived) at Step 2. HSI also owns the `BRA Status` field on its own table (`mb8nv8t3nk6xzed`), which BRA patches from `"Pending"` to `"Complete"` at Step 17 — this is the confirmation loop back to HSI that a record was successfully processed.

**Downstream — RDA (Response Draft Agent):**
BRA's entire output — both the T1 template selection and the T2/T3 Claude-generated strategy — becomes RDA's input via a 28-field webhook payload (Step 18/19). RDA uses BRA's `tone_style`, `urgency_level`, `governance_flag`, `signal_based_consideration`, and `behavioral_interpretation` to draft the actual public response and internal follow-up. BRA never sees or influences RDA's draft text.

**Peer relationship — SIA:**
SIA does not appear anywhere in BRA's or HSI's NocoDB writes or status fields, reinforcing that SIA operates outside this per-record webhook chain (consistent with a separate aggregation process). Not directly confirmed by a dedicated SIA audit — flagged for confirmation when SIA is audited directly.

**Position in the 8-agent chain:**
`ALA → EIP → ESS → HSI → SIA → BRA → RDA → MRA`
BRA sits between HSI (interpretation) and RDA (drafting) — it is the strategic bridge, translating interpreted signal into actionable-but-ungoverned-in-detail response strategy.

### T1 BRANCH (Nodes 9–10)

**Node 9 — Step 9a: T1 Template Selection** (Code)

Hash: `Math.imul(31, h) + charCode`, accumulated per character of `hsi_record_id` as string, then `Math.abs()`.
Filter: `templates.filter(t => t["Signal Category"] === dominant_pole)`. If `dominant_pole` is falsy, defaults to `"Negative"`. Falls back to full pool if no filtered match.

Attempts to override `governance_flag` to `"Flag"` if:
- `signal_type === 'Dignity-Risk Signal'` OR

**✅HIGH — Confirmed connected to Step 10** (Miguel's direct n8n canvas observation, August 22, 2026 — overrides the empty `connections.main` array shown in every JSON export batch of this node across this audit). T1 records do flow through this node's output into the shared governance path.

## 5. TEMPLATE SELECTION LOGIC (T1)

**Table:** `mafv9by73ebama7`, limit 200.

**Algorithm:**
1. Filter templates by `Signal Category === dominant_pole` (default `"Negative"` if `dominant_pole` is falsy).
2. Fall back to the full unfiltered pool if the filter yields zero matches.
3. Generate seed: `Math.imul`-based hash of `hsi_record_id` as string, absolute value.
4. Select: `pool[seed % pool.length]`.
5. Same `hsi_record_id` always selects the same template — deterministic, reproducible, auditable.

**Fields consumed from template record:** `Template Name` → `solution_type`; `Signal Category` → filter key; `Signal-Based Consideration` → `signal_based_consideration`; `Id` → `t1_template_id`.

## 7. GOVERNANCE & HALT ENFORCEMENT

**Two governance layers, both confirmed active for all records regardless of tier:**

**Layer 1 — Pre-flag (Step 7):** `commercial_risk_preflag` set `true` before the tier split if `signal_type` is `Dignity-Risk Signal` or `Masked Negative Signal`. Runs deterministically for every record.

**Layer 2 — Governance Gate (Step 10):** Merges `commercial_risk_flag` (from Claude, or T1 hardcode) with `commercial_risk_preflag`: final flag = `commercial_risk_flag || commercial_risk_preflag || false`. Confirmed as the shared convergence point for both branches.

**Halt enforcement (Step 11):**
- Trigger: `governance_flag === "Halt"`
- Only reachable via the T2/T3 Claude output — T1's `governance_flag` can only be `"None"` or `"Flag"` (from Step 9a/9b), never `"Halt"`. Halt is exclusively a Claude-judgment outcome.
- Action: `throw new Error(...)`, terminating the record.
- ⚠️ No NocoDB error-record write, no status field update. See Section 4, Node 16, and Open Gap #5.

**T1 governance coverage — now confirmed live, with a live gap:**
- `commercial_risk_flag` hardcoded `false` at Step 9a, but can still be elevated to `true` at Step 10 via `commercial_risk_preflag` (Layer 1) if `signal_type` matches Dignity-Risk or Masked Negative.
- `governance_flag` starts `"None"` at Step 9a, and Step 9b's override attempt is the only mechanism to elevate it to `"Flag"` for T1 records — confirmed reaching Step 10, but the override's trigger condition is very likely broken (see Node 10, Section 4). This is a live, uncaught governance coverage gap for T1 dignity/trust signals, not a dead/inert node.
